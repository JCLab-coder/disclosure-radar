# 위키를 코드·설정·서버와 대조하는 점검(린트)

- 정한 날: {{넣은 날 YYYY-MM-DD}} (이 프로젝트에 넣은 날. 처음 만든 날은 2026-10-03)
- 누가 정함: 항목마다 다르다. 각 항목 끝 괄호는 이 방식을 처음 만든 프로젝트(disclosure-radar)에서 누가 정했는지다. 이 프로젝트에서 어떻게 다루는지는 [[wiki-check-hook]] 의 "이 프로젝트에 넣음"과 같다.
- 상태: 유지
- 관련: [[index]], [[log]], [[wiki-check-hook]]

## 결정

- 위키를 점검하는 절차를 이 페이지에 남겨, 다음 세션도 같은 방법으로 점검한다. (사용자)
- 언제 점검하는지를 `CLAUDE.md`·`AGENTS.md` 규칙에 넣는다(규칙 12). (사용자)
- 언제 점검하는지는 아래와 같다. (AI 기본값)
  - 작업을 시작할 때: 아래 "가벼운 점검"을 돌린다. 걸린 커밋이 있으면 작업 전에 사용자에게 알리고, 그 변경을 누가 정했는지 묻는다(규칙 2 의 "확인 안 됨"). 이미 [[log]] 에 경위가 적힌 커밋이면 그렇다고만 알린다.
  - 사용자가 요청할 때: 아래 "전체 점검"을 한다.
  - 서버에 배포하기 전: 가벼운 점검을 돌린다. 배포한 뒤에는 전체 점검의 "서버" 칸을 다시 보고, 서버가 어느 커밋인지 위키에 적는다. 서버가 없는 프로젝트는 이 줄을 건너뛴다.
- 점검은 읽기만 한다. 찾은 것은 먼저 보고하고 고치지 않는다. 사용자가 고치라고 하면 고친다. (AI 기본값)
- 전체 점검을 하면 아래 "점검 기록"에 날짜, 대조한 HEAD, 결과 요약을 한 줄로 더한다. 새 기록은 맨 아래에 더한다. 가벼운 점검만 한 것은 적지 않는다. (AI 기본값)

## 이유

- 커밋 전 훅([[wiki-check-hook]])은 위키 안의 형식(변경 기록, 근거, 링크)만 보고, 위키가 코드와 맞는지는 보지 않는다. 처음 만든 프로젝트에서 사용자가 코드만 고친 커밋이 위키에 반영되지 않은 채 남았고, 서버도 그 전 코드였다. 이런 어긋남은 사람이나 AI 가 대조해야 찾을 수 있다.
- 작업 시작 때 가벼운 점검을 하는 이유: 위키를 거치지 않은 커밋은 다음 세션이 위키만 읽으면 모른다. 커밋 기록만 보면 되므로 빠르다.

## 가벼운 점검: 위키를 고치지 않고 다른 파일만 바꾼 커밋 찾기

저장소 폴더에서 돌린다. 기준은 아래 "점검 기록"의 마지막 "대조한 HEAD" 다. 그 뒤 커밋 중 `wiki/` 밖 파일만 바꾸고 `wiki/` 는 하나도 고치지 않은 커밋을 찍는다. 점검 기록이 아직 없으면 그렇다고 알리고 전체 기록을 본다.

```sh
base=$(grep -o '대조한 HEAD `[0-9a-f]*`' wiki/decisions/wiki-lint.md | tail -1 | grep -o '[0-9a-f]\{7,\}')
if [ -z "$base" ]; then echo "점검 기록에 기준이 없어 전체 기록을 본다."; range=HEAD; else range="$base..HEAD"; fi
git log --reverse --format=%h "$range" | while read c; do
  f=$(git show --name-only --format= "$c")
  if ! echo "$f" | grep -q '^wiki/'; then git log -1 --format='%h %s' "$c"; fi
done
```

- 아무것도 안 나오면 통과다.
- 이 점검이 못 찾는 것: 위키를 일부만 고친 커밋(코드 두 곳을 바꾸고 위키는 한 곳만 고친 경우), 커밋하지 않은 변경, 서버만 바뀐 것(서버 변수·설정을 직접 바꾼 경우).
- 걸린 커밋의 경위를 [[log]] 에 적은 뒤에도 기준이 그대로면 그 커밋은 계속 나온다. 다음 전체 점검에서 기준이 넘어가면 나오지 않는다.

## 전체 점검: 순서

1. 읽기: [[index]] 와 위키의 모든 페이지를 읽는다. 아래 "이 프로젝트에서 대조할 것"의 파일을 읽는다. `.gitignore`, `.githooks/*`, `scripts/*` 를 읽는다. `git log --oneline` 으로 마지막 점검 이후 커밋을 본다.
2. 형식 점검(기계):
   - `node scripts/check-wiki.mjs`: 변경 기록, 근거, 링크.
   - 디스크의 위키에서 없는 링크, 이어지지 않은 페이지, 나가는 링크 없는 페이지를 센다. 아래 스크립트는 큰따옴표 안의 링크도 센다(옵시디언과 같다). 그래서 근거 원문 속 `[[…]]` 가 여기서만 나올 수 있다. 그런 것은 고치지 않는다(원문이라서).

     ```sh
     node -e '
     const fs=require("fs"),path=require("path");
     const files=require("child_process").execSync("git ls-files wiki").toString().trim().split("\n").filter(f=>f.endsWith(".md"));
     const name=f=>path.basename(f,".md"),pages=new Set(files.map(name)),out={},inn={};
     files.forEach(f=>{out[name(f)]=new Set();inn[name(f)]=new Set()});
     for(const f of files)fs.readFileSync(f,"utf8").split("\n").forEach((l,i)=>{
       for(const m of l.replace(/`[^`]*`/g,"").matchAll(/\[\[([^\]|#]+)(?:[#|][^\]]*)?\]\]/g)){
         const n=m[1].trim();if(pages.has(n)){out[name(f)].add(n);inn[n].add(name(f))}else console.log("없는 링크",f+":"+(i+1),n)}});
     console.log("페이지",files.length,"| 이어지지 않음",Object.keys(inn).filter(n=>!inn[n].size),"| 나가는 링크 없음",Object.keys(out).filter(n=>!out[n].size));'
     ```

   - 목차: `wiki/decisions`·`references`·`lessons` 의 페이지가 모두 [[index]] 에 있는지 본다. 디스크와 `git ls-files wiki` 의 `.md` 수가 같은지 본다(커밋하지 않은 페이지).
   - `diff CLAUDE.md AGENTS.md` 가 비어 있는지.
   - starter 자리 표시가 남지 않았는지: `grep -rnE '\{\{[^}]+\}\}' CLAUDE.md AGENTS.md wiki` 가 아무것도 찍지 않아야 한다.
3. 결정 대 코드: 결정 페이지의 "결정" 항목을 하나씩 코드와 맞춰 본다. 값이 코드에 있는 것은 그 줄을 찾아 비교한다.
4. 설정:
   - `git check-ignore -v .env wiki/.obsidian/app.json` 과, 위키가 커밋하지 않는다고 적은 다른 파일: `.gitignore` 에 실제로 있는지.
   - `git config core.hooksPath` 가 `.githooks` 인지, `ls -l .githooks`(실행 권한).
   - 위키가 가리키는 커밋 해시가 있는지(`git log -1 <해시>`).
   - `.env` 키 이름. 값은 찍지 않는다(이름과 "10자 이상인지" 정도만).
5. 서버(읽기만, 서버가 없으면 건너뜀): 배포·설정 바꾸기·즉시 실행은 하지 않는다.
   - 마지막 배포가 마지막 코드 커밋보다 뒤인지, 서버 설정(시작 명령, 일정, 저장 공간 등)이 위키와 같은지.
   - 서버 변수는 값을 그대로 찍지 않는다. 이름만, 그리고 로컬 `.env` 와 "같음/다름"만 찍는다.
   - `git diff --stat <서버에 올린 커밋> HEAD -- <코드 파일>`: 서버에 반영되지 않은 코드 변경.
6. 같은 내용이 두 곳에 있는 것: 목차 요약과 페이지, 결정 페이지끼리, 자료와 결정. 숫자·이름으로 찾는다(`grep -rn -e '<값>' wiki`).
7. 날짜가 박힌 값: 자료 페이지와 확인 칸의 수(페이지 수, 파일 수)는 그때의 값이다. 지금과 다르면 틀린 것이 아니라 "그때 값"이라고 밝히는 덧붙임이 필요한지 본다.
8. 보고: ① 틀리거나 낡은 곳, ② 목차에 없는 페이지, ③ 같은 내용이 다르게 적힌 곳, ④ 아직 "확인 안 됨"인 결정, ⑤ 직접 확인한 것(명령과 범위), ⑥ 확인하지 못한 것으로 나눈다.

## 이 프로젝트에서 대조할 것

전체 점검의 1·3·5 단계에서 보는 것을 프로젝트에 맞게 적는다. 처음 정할 때와 바뀔 때 고친다.

- 코드 파일: {{예: src/ 아래 전부, package.json}}
- 결정 페이지의 값이 들어 있는 곳: {{예: 상수 이름과 파일}}
- 서버: {{예: 없음 / 서비스 이름과 설정을 읽는 명령. 값을 찍지 않는 명령만}}

## 고칠 때 주의

- 다른 페이지가 줄 번호로 가리키는 곳이 있으면, 그 위에 줄을 더할 때 번호가 밀린다. 덧붙임은 기존 줄 끝에 괄호로 단다.
- 결정·자료는 지우지 않고 덧붙인다. [[log]] 는 새 줄만 맨 위에 더한다.
- 점검 장치·규칙 파일(`CLAUDE.md`, `AGENTS.md`, `.githooks/`, `scripts/`, [[wiki-check-hook]])을 고치는 것은 다른 고침과 따로 커밋한다(규칙 11).
