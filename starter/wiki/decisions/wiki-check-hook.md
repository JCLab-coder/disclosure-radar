# 커밋 전에 위키와 비밀값을 점검하는 git 훅을 둔다

- 정한 날: {{넣은 날 YYYY-MM-DD}} (이 프로젝트에 넣은 날. 처음 만든 날은 2026-10-03)
- 누가 정함: 항목마다 다르다. 각 항목 끝 괄호는 이 방식을 처음 만든 프로젝트(disclosure-radar)에서 누가 정했는지다. 이 프로젝트에서 어떻게 다루는지는 아래 "이 프로젝트에 넣음".
- 상태: 유지
- 관련: [[index]], [[log]], [[wiki-lint]], [[checker-self-edit]]

## 결정

- [[log]] 의 지난 기록은 고쳐 쓰지 않는다. 새 기록을 맨 위에 더한다. (사용자)
- 규칙만으로는 빈틈이 생기므로 커밋 전에 위키를 점검하는 스크립트를 git 훅으로 건다. 문제가 있으면 커밋이 안 된다. 훅 파일도 저장소에 넣는다. (사용자)
- 위키 점검은 세 가지를 본다. (사용자)
  - `wiki/log.md` 의 지난 줄이 바뀌거나 지워졌는지
  - 결정 페이지(`wiki/decisions/*.md`)의 "## 근거" 칸 줄이 지워졌는지
  - `[[링크]]` 가 없는 페이지를 가리키는지
- 위키 점검 방법 (AI 기본값)
  - 스크립트는 `scripts/check-wiki.mjs`(Node, 의존성 없음). 스테이지된 내용을 마지막 커밋(HEAD)과 비교한다. 작업 트리는 보지 않는다.
  - 변경 기록: HEAD 의 빈 줄이 아닌 줄이 순서대로 모두 그대로 남아 있어야 한다. 새 줄은 어디에 더해도 된다. 머리말 줄을 고쳐도 막힌다.
  - 근거 칸: HEAD 의 근거 줄이 같은 페이지 근거 칸에 글자 하나 다르지 않게 있어야 한다. 줄을 고치는 것도 지운 것으로 본다(원문을 줄이는 것을 막으려는 것이다). 근거를 더할 때는 새 줄로 더한다.
  - 결정 페이지 파일을 지우는 것도 막는다. 결정을 뒤집을 때는 페이지를 지우지 않는다는 [[index]] 쓰는 규칙에 맞춘 것이다.
  - 링크: git 에 올라간 `wiki/` 안의 `.md`(`git ls-files wiki/`, `wiki/.obsidian/` 제외)에서 `[[이름]]` 을 찾아, 같은 이름의 `.md` 가 있으면 통과. `` `…` `` 코드 안과 큰따옴표 `"…"` 안은 보지 않는다. 근거의 대화 원문은 큰따옴표 안에 그대로 적는데, 그 안의 `[[…]]` 는 링크가 아니라 사용자가 한 말이기 때문이다. 커밋하지 않은 새 페이지를 가리키는 링크는 그 페이지를 `git add` 하기 전까지 없는 페이지로 본다.
- 비밀값 점검: 커밋(모든 파일과 커밋 메시지)에 `.env` 의 실제 값이 들어가면 막는다. 값은 화면에 찍지 않고 키 이름과 파일·줄 번호만 알린다. (사용자)
  - 스크립트는 `scripts/check-secrets.mjs`. 저장소 폴더의 `.env` 를 `node:util` 의 `parseEnv` 로 읽는다. 6자보다 짧은 값은 흔한 글자와 겹치므로 보지 않는다. `.env` 가 없는 컴퓨터에서는 "`.env` 가 없어 비밀값 점검을 건너뜁니다"라고 알리고 넘어간다. (AI 기본값)
- 훅은 작업 트리의 점검 스크립트가 아니라 마지막 커밋(HEAD)에 있는 점검 스크립트를 돌린다. 커밋 안에서 점검 스크립트를 고쳐도, 그 커밋은 고치기 전 스크립트로 점검된다. (사용자)
  - 훅은 `git show HEAD:scripts/<이름>` 을 임시 폴더에 꺼내 `node` 로 돌리고 끝나면 지운다. HEAD 에 그 스크립트가 없으면(첫 커밋, 새로 더한 스크립트) 스테이지된 것을 돌리고 "마지막 커밋에 없어 스테이지된 것을 돌립니다"라고 알린다. 둘 다 없으면 커밋을 막는다. (AI 기본값)
- 점검 장치나 규칙 파일이 바뀌는 커밋은 따로 표시해 사람이 알아보게 한다. (사용자)
  - 표시는 `scripts/check-guard.mjs` 가 한다. 막지는 않는다. pre-commit 에서 바뀌는 파일을 화면에 알리고, commit-msg 에서 메시지 첫 줄 앞에 `[점검·규칙 변경]` 을 붙이고 첫 줄 아래에 "바뀐 점검 장치·규칙 파일: …" 줄을 넣는다. (AI 기본값)
  - 표시하는 파일: `.githooks/` 아래 전부, `scripts/` 아래 전부, `CLAUDE.md`, `AGENTS.md`, 이 페이지(`wiki/decisions/wiki-check-hook.md`). 목록은 `check-guard.mjs` 안에 있다. (AI 기본값)
  - 지난 커밋 중 점검 장치·규칙을 바꾼 것은 훅과 상관없이 git 기록으로 찾는다: `git log --oneline -- .githooks scripts CLAUDE.md AGENTS.md wiki/decisions/wiki-check-hook.md` (AI 기본값)
- 훅은 `.githooks/pre-commit`·`.githooks/commit-msg` 이고 `git config core.hooksPath .githooks` 로 켠다. 이 설정은 `.git/config` 에 들어가 저장소와 함께 옮겨지지 않으므로, 새로 받은 저장소마다 한 번 돌린다. (AI 기본값)
  - 저장소에서 `core.hooksPath` 를 바꾸면 전역 훅(`git config --global core.hooksPath`)이 돌지 않는다. 그래서 두 훅은 전역 훅이 있으면 먼저 부른다.
  - 훅 순서: pre-commit 은 전역 훅 → 표시 알림 → 비밀값 점검 → 위키 점검. commit-msg 는 전역 훅 → 메시지 비밀값 점검 → 표시 붙이기.
  - `package.json` 의 `prepare` 같은 것으로 자동으로 켜지 않는다. 빌드 서버의 설치 단계에서도 돌아 git 이 없는 곳에서 실패할 수 있기 때문이다.
- `git commit --no-verify` 로 건너뛸 수 있다. 사용자가 시키지 않으면 쓰지 않는다. (AI 기본값)
- 장치가 막지 못하는 빈틈은 규칙으로 막는다. `CLAUDE.md`·`AGENTS.md` 규칙 11: 점검에 막히면 통과시키려고 규칙 파일·점검 스크립트·훅·위키의 결정을 고치지 않고 사용자에게 묻는다. 규칙이나 장치를 바꿔야 하면 먼저 묻고, 그 변경만 따로 커밋한다. (사용자. 규칙 11 에 `--no-verify` 를 함께 적은 것과 문장은 AI 가 쓴 것이다)

## 이유

- 처음 만든 프로젝트에서, 위키를 줄여 달라는 요청에 AI 가 [[log]] 의 지난 기록을 고쳐 쓰면서 "실제로 돌려 보지는 않음" 같은 단서가 빠졌다. 규칙만으로는 빈틈이 생겨 장치를 만들었다.
- 비밀값 점검을 저장소에 둔 것은, 한 컴퓨터의 전역 훅은 저장소를 받은 다른 컴퓨터에 없기 때문이다.
- 마지막 커밋의 스크립트를 돌리게 한 것은 [[checker-self-edit]] 때문이다. 작업 트리의 스크립트를 돌리면 같은 커밋 안에서 장치를 고쳐 통과시킬 수 있었다.

## 이 방법이 막지 못하는 것 (알고 둔 한계)

- 훅 파일(`.githooks/*`) 자체는 git 이 작업 트리의 것을 돌린다. 작업 트리의 pre-commit 을 고치면 그 커밋부터 점검이 빠진다(commit-msg 를 그대로 두면 표시는 붙는다).
- 점검 스크립트를 고친 커밋을 먼저 따로 커밋하면 그다음 커밋부터 고친 스크립트가 쓰인다. 막지 않고, 고친 커밋에 표시가 붙어 사람이 보게 한다.
- 비밀값을 바꿔 적은 것(나눠 적기, 인코딩, 일부만 적기), `.env` 에 없고 서버 변수에만 있는 값, 이미 커밋된 기록.
- 훅을 켜지 않은 컴퓨터(`core.hooksPath` 를 설정하지 않은 곳), `--no-verify`.
- 큰따옴표 안의 깨진 링크. 옵시디언 같은 도구는 큰따옴표 안의 `[[…]]` 도 링크로 세므로, 근거 원문 속 `[[…]]` 가 옵시디언에서는 없는 링크로 보일 수 있다.
